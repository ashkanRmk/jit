# P2.0 — Streamed Git process with backpressure

Precondition gap found at kickoff: implementation.md §1 expects `ProcessRunner` to offer "a suspendable
stream API for backpressure". Phase 0/1 only had `run(_:)`, which buffers all of stdout. The history
reader (ADR-0010) needs a long-lived `git log` that costs nothing while nobody scrolls.

## Behavior
- `ProcessRunner.stream(_ spec) -> ProcessStream`; `GitEngine.stream(_ command)` adds Git's path,
  global options and the sanitized environment exactly like `run`.
- The child is launched lazily on the first `read()`, with the same `posix_spawn` setup as `run`
  (shared `SpawnedChild.spawn`: own session/process group, stdin `/dev/null`, close-on-exec).
- `read(maxBytes:)` resumes the stdout Dispatch read source, delivers the next chunk, and suspends the
  source again. While no read waits, the pipe fills and the child blocks in `write(2)`: zero CPU in both
  processes and no parked thread.
- stderr is always drained (last 64 KiB kept) so it can never deadlock the child.
- `nil` = end of output and an accepted exit status; an unaccepted status throws the same mapped
  `processFailed` as `run`.
- Cancelling the task awaiting `read()`, calling `terminate()`, or releasing the `ProcessStream` sends
  SIGTERM to the group, SIGKILL after the grace period.
- A child that exits leaving unread data in the pipe keeps that data readable (no grace-period kill
  unless other group members still hold the pipe).

## Failure cases
Launch failure → thrown on the first `read()`. Concurrent reads → `internalError` (one reader only).

## Tests (`ProcessStreamTests`)
`readsAllOutputThenEnds`, `respectsMaxBytes`, `idleStreamBlocksChildWithoutCPU` (child CPU < 5 ms over
500 ms of not reading `/usr/bin/yes`), `cancellingAReadKillsTheGroup`, `releasingTheStreamKillsTheChild`,
`exitFailureIsMapped`, `slowConsumerAfterExitGetsEverything`, `launchFailureSurfacesOnFirstRead`.
