# P4.1 — Operation framework and execution context

Design: §4.2–§4.5, §4.11. ADRs: 0015, 0032.

## Behavior
- One serialization primitive: the Phase 3 `actor RepositoryHandle` write gate (`performExclusive`, strict
  FIFO across suspension points). Every Phase 4 mutation runs inside it; reads stay `nonisolated`.
- `RepoStateToken` (HEAD OID, HEAD ref, FNV digest of `for-each-ref`, operation state) is captured when a sheet
  is prepared; mutations call `ensureCurrent` inside the gate and throw `.staleSnapshot` if anything moved.
  (Phase 3's `RepoRevision` stays the mutation counter; the token is the new "what did the user see" check.)
- `ExecContext { identity, auth: .nonInteractive, network: .systemDefault }`; `GitEnvironment.remoteCommand`
  adds `-c protocol.ext.allow=never -c protocol.fd.allow=never`, `GIT_SSH_COMMAND` (BatchMode, strict host
  keys), `GCM_INTERACTIVE=never`, no timeout. Base env (all commands): C locale, `GIT_TERMINAL_PROMPT=0`,
  failing askpass, no editors.
- Identity applied only through env: committer always; author only for commits Jit creates (merge, revert,
  stash). No identity → `.noActiveProfile` before anything runs.
- `ProgressParser` splits stderr on CR/LF bytes; `ProgressSink` throttles to ≤ 10 Hz (phase changes and 100 %
  always pass) into an `AsyncStream` the consumer creates with `.bufferingNewest(1)`.
- `GitErrorClassifier` maps C-locale stderr to `FailureKind` (§16.4) with sanitized detail, listed paths and
  `remote:` lines; `GitCoreError.failed(ClassifiedFailure)`.
- `ConfirmationToken` has an internal initializer; only `ConfirmationRequest.confirm()` mints one; destructive
  methods verify the token names exactly their `DestructiveAction`.

## Failure cases
- Hanging credential prompt → impossible (askpass `/usr/bin/false`, no TTY); local HTTP 401 fails in ~50 ms.
- `GIT_PROTOCOL_FROM_USER=0` is not set: it would block top-level `file://` remotes (ADR-0032).
