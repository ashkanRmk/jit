# P7.4 Git resolution and the "no Git" path

**Behaviour.** `GitLocator`: `JIT_GIT_PATH` (debug) → custom Git (`PreferencesStore.customGitPath`) → bundled
→ Homebrew/`/usr/local` (debug) → Apple's Git inside an installed Xcode/CLT, never the shim. Settings ▸ Git
shows the Git in use (version, source, path). "Choose Git…" validates a Git before adopting it (it starts,
version ≥ minimum, `--exec-path` exists) and shows an inline error if it fails. "Use Bundled Git" resets.
When no usable Git exists and no developer tools are installed, an "Install Command Line Tools…" button runs
`xcode-select --install` — only on that click. A repository tab that fails with `gitNotFound`/`gitTooOld`
shows "Git Settings…" instead of "Locate…". `GitEngine.setUserGitPath` re-resolves on the next command; a
probe that started under the old choice is not cached.

**Deviation.** The design's separate onboarding sheet became the Settings ▸ Git pane plus the error card
button: one place, standard Settings, no duplicate UI. There's no "Learn more" link, because no local help
page exists.

**Tests.** `GitLocatorTests` (`gitLocatorPrefersCustomThenBundled`, `releaseIgnoresHomebrewAndUses…`,
`gitLocatorSkipsXcrunShimWithoutCLT` — the shim path is never even probed), `GitValidationTests`
(`gitLocatorRejectsOldVersion`, missing exec-path or file, `setUserGitPathSwitchesTheGitInUse`).
